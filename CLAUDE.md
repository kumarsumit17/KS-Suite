# KS-Suite workspace

Eight independent apps, each its own git repo, plus `ks-utility`, a repo of generic utility code. Six apps are Kotlin apps; `ks-download-manager` and `ks-forge` are desktop-only Rust/Tauri apps. This file holds suite-wide rules; each repo's own `CLAUDE.md` holds its stack, constraints, and commands. Read that one before working in a repo.

## Specs
- All suite-wide specs live in `specs/` in the repository root, as an Open Knowledge Format (OKF) v0.2 bundle. Each app keeps its own specs in its repo's `specs/`. Start at `specs/index.md`.
- One topic per file. Every file except `index.md` and `log.md` starts with YAML frontmatter: `type` (required: `Specification`, `Policy`, `Plan`, `Playbook` or `Reference`), `title`, `description` (one sentence), `tags`.
- When a spec is added: list it in `specs/index.md` with its description. When a spec is added or changed: add a line under today's date (`# YYYY-MM-DD`, newest first) in `specs/log.md`.
- Link between specs with relative markdown links (`[Dependencies](dependencies.md)`), so they also work on GitHub.
- Links to another repository use the full GitHub URL; relative links are only for files inside this repository.

## Rules that apply to every repo
- Exception: `ks-download-manager` and `ks-forge` are desktop-only Rust/Tauri apps with no Android version, so the Kotlin, Gradle and package-root rules below do not apply to them. Each one's own `CLAUDE.md` defines its stack. All other rules (signing material, tag versions, Conventional Commits, no analytics or ads) still apply.
- Kotlin only. Gradle Kotlin DSL (`*.gradle.kts`) with a version catalog at `gradle/libs.versions.toml`. JDK 17.
- Package root is `com.ks.<app>`.
- Never commit or print signing material: `keystore.properties`, `*.jks`, `*.keystore`, or the `SIGNING_*` env vars.
- A new app repository gets its signing secrets first: before any code, CI or release work, the owner sets the four secrets from the suite keystore (alias `ks-release`) and they are checked. See `specs/versioning-signing.md`, "A new repository: signing first".
- Version numbers come from git tags via `-PversionName` and `-PversionCode`. Every app tags each release with its platform: `android-vMAJOR.MINOR.PATCH`, `google-tv-v…`, `mac-v…`, `windows-v…` or `chrome-v…` (a Chrome extension), so each platform build has its own version; one-platform apps use their prefix too. A plain `vMAJOR.MINOR.PATCH` still releases every platform at once. An app that checks for updates ships one plain bridge release before its first platform tag. Never hardcode versions in `build.gradle.kts`. Checked by ks-utility's `ks-suite-check` (v0.15.0 and later). See `specs/versioning-signing.md`.
- DEV, test, approval, production: every feature or fix is made on `dev` (which starts from the latest production release on `main`), tested automatically, built as a DEV build (the release workflow's rehearsal) and tested by the owner by hand; a production release needs the owner's explicit approval for that app and platform. Exceptions: an app's first release on a platform (automated tests and signing are enough), and the initial rollout on ks-utility v0.18.4. A new ks-utility version never starts a production release by itself. DEV builds install next to PROD (Android/Google TV application ID and macOS bundle ID with `.dev`, own Windows MSI UpgradeCode, " DEV" names and icons, signed with a separate DEV key; DEV data never reaches PROD and every install keeps its data per OS user; published as workflow artifacts, never as releases); PROD identities never change; the release pull request from `dev` to `main` records the owner's approval. Android signing is mandatory and verified; macOS and Windows may ship unsigned; every release has `SHA256SUMS` and records its ks-utility version. Never commit or release while a test fails; a feature raises MINOR, a fix raises PATCH. See `specs/release-cycle.md`.
- Commits follow Conventional Commits (`feat:`, `fix:`, `feat!:`, `chore:`).
- No analytics, crash-reporting, or ad SDKs in any app. Checked by ks-utility's `ks-suite-check` (v0.15.0 and later).
- No default framework icon (Kotlin or Compose logo, Android's default robot, Tauri's logo) in any build on any platform: every launcher icon, TV banner, `.app`/`.dmg`, installer, window, taskbar, tray and extension icon is the app's own. Checked by ks-utility's `ks-suite-check` (v0.15.0 and later) for the defaults it can recognise; see `specs/conventions.md`, "App icons".
- Every app supports English and Hindi through `ks-utility`: interface text in its language files (`en.json`, `hi.json`) with the shared catalogue, the suite's language rule (follow the system, allow a choice, remember it), the Hindi style guide, and the language-file check in the app's tests (Checked by ks-utility's `ks-suite-check` (v0.15.0 and later)). See ks-utility's `specs/languages.md`.
- Every app checks for its updates with ks-utility's updater. Checked by ks-utility's `ks-suite-check` (v0.15.0 and later); the only exception is a `ks-suite-check.json` with `no-updater` and the reason (ks-utility's `specs/suite-check.md`).
- Shared code lives only in `ks-utility`, and only when it is generic: reused across apps, with no application-specific logic. Every app takes `ks-utility` as a dependency pinned to a version tag (lock files and submodule entries keep the exact commit): the Kotlin apps as a git submodule at `ks-utility/` included with `includeBuild("ks-utility/kotlin")`, the Tauri apps (`ks-download-manager`, `ks-forge`) as git dependencies in their `package.json` and `src-tauri/Cargo.toml`. Never edit the submodule copy inside an app; change `ks-utility` itself, then move the app's pin. See `specs/cross-repo.md` and `ks-utility/CLAUDE.md`.
- `ks-utility` versioning: tags are `vMAJOR.MINOR.PATCH`; while in `0.x` a new helper or a behaviour change raises MINOR and a fix raises PATCH. A pushed tag is never moved or deleted; a mistake gets a new tag. ks-utility tags at most once a day, collecting its changes on `dev` (an urgent security fix excepted), so app releases are not stopped by tag after tag. Every app moves to a new ks-utility tag the same day it is released: its own commit `chore: move ks-utility to vX.Y.Z`, tested and pushed to `dev`, done by the ks-utility bump workflow; a release workflow refuses a pin that is not the newest tag. Apps call ks-utility's shared workflows at `@main`, always its newest release (`specs/cross-repo.md`). Rules that code can carry live in ks-utility and its `ks-suite-check`; KS-Suite keeps process rules and pointers (`specs/rule-architecture.md`). Publishing to public registries (crates.io, npm, Maven Central) is a future step, deferred until the helpers are stable. Details: ks-utility's `specs/usage.md`.
- Every repo has the graphify setup (`.claude/`, and a `graphify` section in its `CLAUDE.md`). `graphify-out/` is generated and git-ignored. `ks-tv-launcher` uses its own code graph (`scripts/kb.py`) instead.
- Every app repo has the same platform folders: `tv/google-tv/`, `desktop/mac/`, `desktop/windows/`, `mobile/android/` and `mobile/ios/`. All five exist in every app repo, even for platforms the app does not target. Code for one platform goes in its folder; code used by two or more platforms of the same app goes in `shared/` in that repo's root (fixed name), written once and never copied between platform folders; generic code used by several apps goes in `ks-utility`. `ks-utility` is a helpers repo and keeps its own layout. The five folders are checked by ks-utility's `ks-suite-check` (v0.15.0 and later). See `specs/platform-folders.md`.
- Each platform build of every app is optimized for its own OS (engine, rendering, input, look, OS integrations), with as few dependencies as possible and nothing the user must install; genuinely shared code stays in `shared/`. Each app keeps a per-platform plan in its `specs/`. See `specs/platform-folders.md`.
- Branches: only `dev` and `main` in every repo. Commit all work on `dev`; `main` only fast-forwards to `dev` at a release; start new work from `dev` brought up to date with `main`; never create another branch, and delete any that exists once its work is on `dev`. See `specs/release-cycle.md`.
- Changes are scoped to one repo. If a change touches a cross-repo contract (`specs/cross-repo.md`), update the docs on both sides.

## Working efficiently (keep token use low)
- One app at a time: only the active app in `specs/progress.md` is worked on, until it is released with the owner's approval and the owner names the next. Each session starts from `specs/index.md`, `specs/progress.md` and the active app's `specs/progress.md`, and records a checkpoint before it ends. See `specs/working-method.md`.
- Apps follow `specs/architecture-standards.md`: minimal, local-first, zero-cost, with storage and security matched to each app's class (A sensitive, B persistent, C basic).
- Use the knowledge graph first: follow the rules in the `graphify` section at the end of this file. [graphify](https://github.com/Graphify-Labs/graphify) is a development tool only; it is never a dependency of the code and is never bundled or shipped.
- One-time setup on a new machine (owner): `uv tool install graphifyy` (the package name has two y's), then `/graphify .` in Claude Code. The setup in `.claude/` is committed; `graphify-out/` is generated and git-ignored.
- Read only the specs the task needs, and do not re-read a file that has not changed in this session.
- Never read generated files: the app folders' build output (`build/`, `.gradle/`, `node_modules/`, `target/`), `graphify-out/graph.json`.
- Keep command output short (show only failures), and keep summaries brief.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. When the answer is under a Markdown heading, `graphify section "<heading>"` prints that section's text, so the .md need not be opened. These return a scoped subgraph, usually much smaller than GRAPH_REPORT
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- `graphify-out/` is generated and git-ignored: never commit it.
